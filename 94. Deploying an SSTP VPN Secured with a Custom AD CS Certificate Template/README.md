# Lab: Deploying an SSTP VPN Secured with a Custom AD CS Certificate Template

## Overview

This lab documents the end-to-end process of setting up a **Windows Server-based SSTP VPN** secured by a certificate issued from a **custom Active Directory Certificate Services (AD CS) template**. It covers creating the certificate template, issuing and exporting the certificate, configuring the VPN (RRAS) server, binding the certificate to the SSTP listener, and troubleshooting the common client-side connection errors that occur along the way (DNS resolution, certificate trust, revocation checking, and authentication protocol mismatches).

**Lab environment:**
- Domain: `company.local`
- CA Server / RRAS Server: `ADC.company.local` (Active Directory Certificate Services + Routing and Remote Access)
- VPN Type: SSTP (Secure Socket Tunneling Protocol)
- Client OS: Windows 10

**Goal:** Establish a working SSTP VPN connection authenticated with a certificate issued by an internal CA, and resolve every error encountered during setup.

## Task 1 – Create a New Certificate Template

Open **Certificate Templates** (`certtmpl.msc`) on the CA server, duplicate a base template (e.g. IPsec), and open its **Properties**.

On the **General** tab:
- Set **Template display name** to `COMPANY IPsec`
- Set **Validity period** to `2 years`
- Set **Renewal period** to `6 weeks`
- Leave **Publish certificate in Active Directory** unchecked (since the subject name will be supplied manually)

![Create New Template](images/task01-create-new-template.png)

**Why:** A dedicated template lets you control validity, key usage, and enrollment permissions independently from built-in templates, and keeps naming consistent across the organization.

---

## Task 2 – Configure Template Cryptography Settings

On the **Cryptography** tab:
- **Provider Category:** Legacy Cryptographic Service Provider
- **Minimum key size:** `2048`
- **Requests must use one of the following providers:** check **Microsoft RSA SChannel Cryptographic Provider**

![Template Cryptography](images/task02-template-cryptography.png)

**Why:** SSTP relies on SChannel (Schannel.dll) for the TLS handshake, so the certificate's private key must be generated by a CSP that SChannel can use for server authentication — hence selecting the RSA SChannel provider specifically rather than a generic CSP.

---

## Task 3 – Add Server Authentication to Certificate Extensions

On the **Extensions** tab, select **Application Policies** → **Edit**, then add **Server Authentication** alongside the existing **IP security IKE intermediate** policy.

![Server Authentication Extension](images/task03-server-authentication-extension.png)

**Why:** SSTP tunnels PPP over an HTTPS/TLS connection, so the certificate presented by the VPN server must contain the **Server Authentication (1.3.6.1.5.5.7.3.1)** EKU (Extended Key Usage), or Windows will reject it for SSL/TLS server use even if it's otherwise valid for IPsec.

---

## Task 4 – Configure Subject Name to Supply in the Request

On the **Subject Name** tab, select:
- **Supply in the request**

Leave "Build from this Active Directory information" unchecked.

![Subject Name - Supply in Request](images/task04-subject-name-supply-in-request.png)

**Why:** This allows the administrator to manually type the exact FQDN (`ADC.company.local`) as the certificate's Common Name at enrollment time, rather than relying on AD's default computer object naming — important because the VPN clients must resolve and match this exact name.

---

## Task 5 – Issue the Certificate Template on the CA

Open the **Certification Authority** console → **Certificate Templates** → **New** → **Certificate Template to Issue**, then select the newly created **COMPANY IPsec** template (Intended Purpose: *Server Authentication, IP security IKE intermediate*).

![Issue the Certificate](images/task05-issue-the-certificate.png)

**Why:** Creating a template only makes it *available*; it must still be explicitly issued on the CA before any client can enroll for it.

---

## Task 6 – Request the Certificate (Computer Account)

Open `certlm.msc` or add the **Certificates** snap-in via `mmc.exe` and choose to manage certificates for the **Computer account**.

![Computer Account Snap-in](images/task06a-computer-account-snapin.png)

Then, under **Personal → Certificates**, right-click → **All Tasks → Request New Certificate**, and select the **COMPANY IPsec** template. Notice the warning: *"More information is required to enroll for this certificate. Click here to configure settings."*

![Request Certificate Personal](images/task06b-request-cert-personal.png)

**Why:** Because the template was configured to require the subject name be **supplied in the request** (Task 4), Windows can't auto-populate it and prompts for manual configuration before enrollment can proceed.

---

## Task 7 – Add the Common Name (Subject) to the Request

Click the warning link to open **Certificate Properties → Subject** tab, and add:
- **Type:** Common name
- **Value:** `ADC.company.local`

This appears in the **Subject name** box as `CN=ADC.company.local`.

![Add Common Name](images/task07-add-common-name.png)

**Why:** The Common Name must exactly match the hostname clients will use to connect (the VPN "Server name or address"), otherwise the TLS certificate name-mismatch check will fail on the client.

---

## Task 8 – Verify Certificate Details

After enrollment, open the issued certificate and inspect the **Certification Path** and **Details** tabs to confirm:
- Certification path: `company-PDC16-CA` → `ADC.company.local`
- **Certificate status:** *This certificate is OK.*
- Signature algorithm: `sha256RSA`
- Validity dates correctly reflect the 2-year period configured in Task 1

![Copy Certificate Details](images/task08-copy-cert-details-to-file.png)

**Why:** Verifying the chain and status here confirms the certificate is correctly issued and trusted *on the server itself* before it's exported for use elsewhere — catching problems early rather than after VPN configuration.

---

## Task 9 – Export the Certificate

From the certificate's **Details** tab, click **Copy to File...** to launch the **Certificate Export Wizard**. Export as:
- **File Format:** DER Encoded Binary X.509 (`*.cer`)
- **Export Keys:** No
- **Include all certificates in the certification path:** No

![Export Certificate](images/task09-export-cert.png)

**Why:** The client machine and the VPN clients don't need the private key (that stays protected on the server) — they only need the **public certificate** so they can validate the server's identity and trust the issuing CA chain.

---

## Task 10 – Add a New VPN Connection on the Client

On the Windows client, go to **Settings → Network & Internet → VPN → Add a VPN connection**:
- **VPN provider:** Windows (built-in)
- **Connection name:** `vpn-sstp`
- **Server name or address:** `ADC.company.local`
- **VPN type:** Secure Socket Tunneling Protocol (SSTP)
- **Type of sign-in info:** User name and password
- **User name:** `COMPANY\ahmed.abdo`

![Add VPN Connection](images/task10-add-new-vpn-connection.png)

**Why:** SSTP is chosen explicitly (rather than "Automatic") because it tunnels over TCP 443, making it firewall-friendly, and it's the protocol type this lab's certificate was built for (Server Authentication EKU).

---

## Task 11 – Troubleshoot: "No such host is known"

Attempting to connect immediately produces:

> **Can't connect to vpn-sstp**
> **No such host is known.**

![No Such Host Error](images/task11-no-such-host.png)

**Root cause:** The client cannot resolve the DNS name `ADC.company.local` — it's likely connecting from outside the corporate network/domain, so there's no DNS server that knows this internal FQDN.

---

## Task 12 – Fix DNS by Adding a Hosts File Entry

Edit `C:\Windows\System32\drivers\etc\hosts` (as Administrator) and add:

```
11.0.0.3    ADC.company.local
```

![Add DNS Record to Hosts File](images/task12-add-dns-record-hosts-file.png)

**Why:** Since there's no reachable DNS server to resolve the internal domain name from the client's current network, a static hosts file entry manually maps the FQDN to the VPN server's public/reachable IP address, allowing the client to resolve the name locally without needing DNS.

---

## Task 13 – Troubleshoot: Certificate Chain Not Trusted

Retrying the connection now produces a new error:

> **Can't connect to vpn-sstp**
> **A certificate chain processed, but terminated in a root certificate which is not trusted by the trust provider.**

![Certificate Chain Not Trusted](images/task13-cert-chain-not-trusted.png)

**Root cause:** DNS resolution now succeeds and the TLS handshake begins, but the client does not have the internal CA's root certificate (`company-PDC16-CA`) in its **Trusted Root Certification Authorities** store, so it cannot validate the chain of trust for the certificate presented by the SSTP server.

---

## Task 14 – Bind the Certificate to the VPN Server

On the RRAS server, open **Routing and Remote Access → Properties → Security** tab and confirm the **SSL Certificate Binding**:
- **Certificate:** `ADC.company.local`

![Bind Certificate to VPN Server](images/task14-add-cert-to-vpn-server.png)

**Why:** This explicitly tells the SSTP (SSL) listener which certificate to present during the TLS handshake — RRAS won't automatically pick the correct one if multiple certificates exist in the computer's Personal store.

---

## Task 15 – Import the Certificate on the Client Machine

On the client, run `certmgr.msc` (or double-click the exported `.cer` file) to launch the **Certificate Import Wizard**. Choose:
- **Store Location:** Local Machine

![Certificate Import Wizard](images/task15-import-cert-on-client.png)

**Why:** Importing to **Local Machine** (rather than Current User) makes the trust decision apply system-wide, which is required since the VPN connection operates at the machine/network level, not per user profile.

---

## Task 16 – Move the Certificate to Trusted Root CAs

Continue the Import Wizard and explicitly select:
- **Place all certificates in the following store**
- **Certificate store:** Trusted Root Certification Authorities

![Move to Trusted Root](images/task16-move-cert-to-trusted-root.png)

**Why:** This directly resolves the Task 13 error — by placing the CA's root certificate into the client's Trusted Root store, the client can now build and validate a complete, trusted certification path when the VPN server presents its certificate.

---

## Task 17 – Troubleshoot: Revocation Server Offline

With trust established, a further connection attempt returns:

> **Can't connect to vpn-sstp**
> **The revocation function was unable to check revocation because the revocation server was offline.**

![Revocation Error](images/task17-revocation-error.png)

**Root cause:** Windows validates certificates by checking a **Certificate Revocation List (CRL)** distribution point, typically published internally by the CA. Since the client is outside the corporate network, it cannot reach that internal CRL endpoint, so revocation status can't be confirmed.

---

## Task 18 – Disable Revocation Checking via Registry

Open the registry editor and navigate to:

```
HKLM\SYSTEM\CurrentControlSet\Services\RasMan\Parameters
```

Create/edit a **DWORD (32-bit) Value**:
- **Value name:** `NoCertRevocationCheck`
- **Value data:** `1` (Hexadecimal)

![NoCertRevocationCheck Registry Value](images/task18-no-cert-revocation-check-registry.png)

**Why:** This registry key tells the RAS/VPN client stack to skip CRL/OCSP revocation checks for the SSTP certificate entirely, working around the unreachable internal CRL. *(Note: this is a practical lab workaround — in production, a properly published and externally reachable CRL/OCSP endpoint is the recommended fix rather than disabling revocation checking outright.)*

---

## Task 19 – Allow MS-CHAP v2 on the VPN Connection

Open the VPN connection's **Properties → Security** tab:
- **Authentication:** select **Allow these protocols**
- Check **Microsoft CHAP Version 2 (MS-CHAP v2)**

![Allow MS-CHAP v2](images/task19-allow-mschapv2.png)

**Why:** The RRAS server's Authentication Methods (bound to RADIUS in this setup) needs a matching authentication protocol on the client side. Without explicitly enabling MS-CHAP v2 (or matching whatever the server allows), the PPP authentication phase fails even after the TLS/SSTP tunnel itself is successfully established.

---

The VPN connection now shows **Connected**, and a `ping` test to an internal resource confirms end-to-end connectivity:

## Summary of Errors & Fixes

| # | Error Encountered | Root Cause | Fix |
|---|---|---|---|
| 1 | `No such host is known` | Client can't resolve `ADC.company.local` via DNS | Added static entry to the client's `hosts` file |
| 2 | `Certificate chain processed, but terminated in a root certificate which is not trusted` | Internal CA root cert not in client's trust store | Imported the CA cert into **Local Machine → Trusted Root Certification Authorities** |
| 3 | `The revocation function was unable to check revocation because the revocation server was offline` | Client can't reach the internal CRL distribution point | Set `NoCertRevocationCheck = 1` (DWORD) under `HKLM\SYSTEM\CurrentControlSet\Services\RasMan\Parameters` |
| 4 | PPP authentication failure after TLS tunnel established | Client's allowed authentication protocol didn't match server (RADIUS) | Enabled **MS-CHAP v2** under the VPN connection's Security properties |

## Key Takeaways

- SSTP requires a server certificate with the **Server Authentication EKU**, generated by an **SChannel-compatible CSP**.
- The certificate's **Common Name must match the FQDN** clients use to connect.
- Full chain of trust (leaf cert → root CA) must exist on **both** the VPN server and every connecting client.
- Revocation checking depends on the CRL being reachable from wherever the client connects — a common point of failure for remote/external clients connecting to an internal CA.
- SSTP establishes a TLS tunnel first; PPP authentication (e.g., MS-CHAP v2) is a **separate, subsequent phase** that must also be correctly aligned between client and RRAS/RADIUS server.
